# 메일 업로드 처리

메일은 다른 문서와 성격이 다릅니다. **같은 것이 여러 벌 들어옵니다.** 같은 메일을 받은
사람마다 저장하고, 스레드가 이어지면 답장마다 원문이 딸려 오고, 첨부는 전달될 때마다
따라옵니다. 그래서 메일만 별도 처리가 있습니다.

---

## 1. 사내 형식(.mysingle) 자동 변환

그룹웨어가 내려주는 `.mysingle` 은 확장자만 다를 뿐 내용은 표준 메일(RFC 822)입니다.
업로드하면 **적재 첫 단계에서 `.eml` 로 바꿉니다.** 이후 파싱·보관·다운로드는 전부
보통 메일과 똑같이 돌아갑니다.

내용을 보고 판단하므로 확장자만 믿지 않습니다.

| 실제 내용 | 처리 |
|---|---|
| 표준 메일 | 그대로 통과 (바이트 동일, 확장자만 `.eml`) |
| 압축(zip) | 안에 든 메일 본체를 꺼냄 |
| HTML 조각 | 표준 메일로 감쌈 (제목 = 파일명) |
| 평문 (utf-8 / cp949) | 표준 메일로 감쌈 |
| 그 외 | 읽기 실패로 안내 |

문서 목록에는 사용자가 올린 이름(`채용개편.mysingle`)이 그대로 보이고, 서버에 보관되는
파일만 `.eml` 입니다. 다운로드하면 `.eml` 로 받아지므로 메일 프로그램에서 바로 열립니다.

관련: `app/ingestion/mailfile.py`

## 2. 같은 메일은 한 건 — Message-ID 기준

같은 메일이라도 **사서함마다 헤더가 다릅니다**(`Received` 등). 그래서 파일 해시로는
같은 메일을 못 잡습니다.

```
A 사서함 사본  hash=46e66e…   ┐
                              ├─ 파일은 다르지만 Message-ID 는 같다
B 사서함 사본  hash=6a1502…   ┘
```

메일에는 발신 시점에 정해지는 고유값 `Message-ID` 가 있고, 사본이 몇 개든 이 값은
같습니다. 그래서 **메일은 Message-ID 로 중복을 판정**합니다.

- 두 번째로 올린 사람에게는 "이미 등록된 문서(같은 메일)"라고 안내합니다.
- **답장·전달은 각자 다른 메일**입니다(Message-ID 가 다름) → 별도 문서로 등록됩니다.
- Message-ID 가 없는 메일도 있습니다 → 그때는 기존대로 파일 해시로 판단합니다.
- 메일이 아닌 문서에는 영향이 없습니다.

관련: `app/ingestion/intake.py`, `DocumentRepository.message_id_lookup`

## 3. 첨부는 별도 문서로

예전에는 첨부가 **검색에는 안 잡히고 용량만 먹었습니다.** 파서가 첨부를 무시했기 때문에
2MB 엑셀이 붙은 메일을 올려도 색인되는 건 본문 몇 줄뿐인데, 서버에는 2.67MB가 그대로
쌓였습니다(base64라 원본보다 1.37배).

지금은 등록할 때 첨부를 꺼내 **각각 하나의 문서로 등록**합니다.

- 첨부의 **폴더·작성부서·열람 권한은 메일과 같습니다.** 같은 자리에서 온 파일이므로
  권한이 어긋날 일이 없습니다.
- 메일과 첨부는 **'메일 첨부' 연관**으로 이어져 문서 상세에서 서로 오갈 수 있습니다.
- 메일을 등록 확정하면 첨부도 함께 확정됩니다(예약 처리·일괄 반입 포함).
- 보관하는 메일에서는 떼어낸 첨부 자리에 안내 문구만 남습니다.

**안전 규칙 두 가지:**

1. 등록하지 못한 형식(`.hwp` 등)은 **메일에서 빼지 않습니다.** 원본이 사라지면 안 되니까요.
2. 첨부가 또 메일이면 **거기서 멈춥니다.** 스레드가 통째로 딸려 올 때 끝없이 번지는 걸
   막습니다(첨부된 메일 자체는 문서로 등록됩니다).

### 같은 첨부가 여러 메일에 붙어 있으면

내용이 같으면 파일 해시가 같으므로 **문서는 하나만** 만들어지고, 두 번째 메일은 기존
첨부 문서에 연결만 됩니다. 스레드를 통째로 올려도 첨부는 한 벌만 저장됩니다.

### 실측

메일 3건(모두 같은 22KB 첨부 포함, 그중 하나는 사서함 사본)을 올렸을 때:

```
① A가 올림 (.mysingle, 첨부 有)        30KB → 등록
② B 사서함 사본 (.eml, 헤더만 다름)     30KB → 중복거부(같은 메일)
③ 스레드 전달 (같은 첨부 재첨부)         30KB → 등록

등록된 문서
  - 채용개편.mysingle    1KB   (첨부를 덜어낸 .eml)
  - 전달.eml            1KB
  - 연차규정.txt        22KB   ← 첨부, 두 메일이 함께 연결됨

올린 파일 합계 89KB → 서버 보관 23KB (26%)
```

관련: `ReviewService._split_mail_attachments`

## 4. 보관 파일 확장자

보관 파일명이 내부 형식 값(`email`)을 쓰던 탓에 `제목.email` 로 저장돼 다운로드해도
더블클릭으로 열리지 않았습니다. 형식별 실제 확장자를 쓰도록 고쳤습니다(`.eml`).

기존에 `.email` 로 저장된 파일은 마이그레이션이 한 번에 이름을 바꿔 줍니다.

```bash
python -m scripts.migrate
```

`documents.message_id` 컬럼 추가도 같은 명령에 포함돼 있습니다. **메일 기능을 쓰기 전에
한 번 실행하세요.**

## 아직 안 한 것 — 인용문 제거

답장은 원문을 인용해 포함하므로, 스레드가 5단계면 마지막 메일만으로 충분한 내용이
5벌 색인됩니다. 검색 상위가 같은 문장으로 채워질 수 있습니다.

인용문을 잘라내도 **메일 사이의 관계는 잃지 않습니다.** 답장·전달 관계는 인용문이 아니라
헤더(`In-Reply-To`, `References`)에 들어 있기 때문입니다.

```
<M1@corp>  답장대상=-          뿌리=-          깊이=0
<M2@corp>  답장대상=<M1@corp>  뿌리=<M1@corp>  깊이=1
<M3@corp>  답장대상=<M2@corp>  뿌리=<M1@corp>  깊이=2
```

지금은 이 헤더를 읽지 않습니다. 인용문 제거를 넣을 때 함께 붙이면 스레드 구조가 오히려
지금보다 정확해집니다(유사도 추측이 아니라 헤더가 알려주는 사실이므로).
