# 예약 업로드 (웹에서 대량으로 올리고 야간에 자동 등록)

웹에서 문서를 한 번에 많이 올려야 할 때 쓰는 기능입니다. **올리는 것**과 **등록하는 것**을
떼어놓아서, 사용자는 파일만 올려두고 실제 처리(AI가 읽고 색인)는 정해진 시간대에
서버가 알아서 합니다.

---

## 왜 나눴나

문서 하나를 등록하려면 파일을 읽고 → LLM 이 요약·분류·키워드를 만들고 → 임베딩을 뽑아
색인합니다. 문서당 수십 초입니다. 200개면 한두 시간이고, 그동안 브라우저는 응답을 기다려야
하는데 **웹 요청은 그렇게 오래 못 삽니다**(프록시·브라우저가 먼저 끊습니다).

그래서:

| | 즉시 처리 | 예약 처리 |
|---|---|---|
| 요청이 하는 일 | 파일 읽기 + AI 자동 채움 + 색인 | **파일 저장만** (수 초) |
| 걸리는 시간 | 문서당 수십 초 | 개수와 무관하게 금방 |
| 사람 검토 | **함** (내가 확인하고 확정) | **생략** (서버 반입과 동일) |
| 한 번에 | 50개 | **개수 제한 없음** (총 2GB) |
| 등록 시점 | 바로 | 처리 시간대(기본 18:00~08:00) |

검토를 생략해도 안전한 이유는 **권한이 AI 판단에서 오지 않기 때문**입니다. 작성부서와 열람
권한은 업로드할 때 고른 **폴더**에서 그대로 옵니다(서버 일괄 반입과 같은 방식).

---

## 쓰는 법 (사용자)

1. **문서 → 문서 등록** 을 펼칩니다.
2. **폴더**를 고릅니다. ← 이 폴더가 작성부서·열람 권한·저장 위치가 됩니다.
3. 파일을 여러 개 선택합니다.
4. 처리 방식에서 **예약 처리** 를 고릅니다.
5. **처리 시작** 시각을 정합니다(기본 18:00). **예약하기**.

### 처리 시작 시각

기본은 설정된 시간대 시작(18:00)이고, 원하는 시각으로 바꿀 수 있습니다. 오늘 그 시각이
이미 지났으면 내일로 잡힙니다.

**지금 바로**를 체크하면 업무시간이어도 즉시 처리합니다. GPU 를 채팅과 나눠 쓰게 되니
급한 경우에만 쓰세요.

> 시각은 **Asia/Seoul 기준**입니다. 화면에 **서버 현재 시각**이 같이 표시되니 확인하고
> 고르세요. 서버 시계가 내 PC 와 5분 넘게 어긋나면 화면 위에 경고가 뜹니다.

### 화면 시각이 실제와 다를 때

시간대 계산이 맞아도 **서버 시계 자체가 틀리면** 예약 시각이 그만큼 어긋납니다.
화면 상단에 이런 경고가 뜨면 시계 문제입니다.

> ⚠️ **서버 시계가 이 PC 보다 8시간 빠릅니다.** 예약한 시각도 그만큼 어긋나 처리됩니다.

서버에서 진단합니다.

```bash
python -m scripts.check_time
```

```
── 서버 시계 ────────────────────────────────────────────
  UTC                   : 2026-08-07 01:06:53
  업무 시간대(Asia/Seoul) : 2026-08-07 10:06:53  ← 화면에 뜨는 시각
  시간대 표기           : KST(UTC+09:00)
  서버 시스템 로컬      : 2026-08-07 01:06:53 (UTC/UTC)
```

- **'업무 시간대' 시각이 실제와 다르다** → 서버 시계가 틀린 것입니다.
  ```bash
  timedatectl                      # 상태 확인
  sudo timedatectl set-ntp true    # 사내 NTP 로 동기화
  ```
  도커로 띄웠다면 컨테이너는 호스트 시계를 따라가므로 **호스트를 먼저** 맞춥니다.
- **시간대 표기가 KST(UTC+09:00)가 아니다** → `.env` 의 `SCHEDULE_TIMEZONE` 을 고치고
  워커를 재시작합니다.

올린 직후 화면 위에 **예약 업로드** 현황이 뜹니다. 대기 / 처리 중 / 등록 완료 / 실패
건수와, 언제부터 처리가 시작되는지 안내가 나옵니다. 실패한 게 있으면 파일명과 사유가
같이 보이고 **실패분 다시 시도** 버튼으로 다시 대기열에 넣을 수 있습니다.

> 관리자에게는 전체 사람의 예약 현황이 보이고, 일반 사용자에게는 **본인이 올린 것만**
> 보입니다.

### 중간에 끊겨도 보낸 것은 남습니다

브라우저가 파일을 **20개(또는 50MB)씩 나눠서** 보냅니다. 요청 하나에 다 실으면 중간에
연결이 끊겼을 때 전부 날아가는데, 나눠 보내면 이미 보낸 묶음은 서버 대기열에 그대로
남습니다.

```
500개 선택
  └─ 25묶음으로 나눠 순서대로 전송
       ├─ 1~12묶음 전송 완료 → 240건 대기열에 안전하게 남음
       ├─ 13묶음에서 연결 끊김 → 그 묶음만 자동 재시도(최대 3회)
       └─ 그래도 실패하면 어느 파일이 안 갔는지 알려줌
```

- 진행 상황이 막대로 표시됩니다 — "예약 240 / 500건".
- 실패한 묶음은 **자동으로 3회까지 다시** 보냅니다(1.5초 → 3초 간격).
- 끝까지 실패하면 안 올라간 파일 이름을 알려줍니다. **그 파일만** 다시 고르면 됩니다.
- 브라우저를 닫아도 이미 보낸 건 처리됩니다.

총 용량이 2GB를 넘으면 **저장하기 전에** 거절합니다. 받아 두고 못 쓰면 디스크만
차지하기 때문입니다.

## 워커 띄우기 (관리자, 1회 설정)

예약된 파일은 워커 프로세스가 처리합니다. 이게 안 떠 있으면 파일은 대기열에 쌓이기만 합니다.

```bash
python -m scripts.ingest_worker              # 상주 실행(시간대 밖이면 대기)
python -m scripts.ingest_worker --now        # 시간대 무시하고 지금 처리
python -m scripts.ingest_worker --once       # 대기열을 한 번만 비우고 종료
python -m scripts.ingest_worker --workers 8  # 동시 처리 수(기본 4)
```

### systemd 로 상주시키기

`/etc/systemd/system/hr-ingest-worker.service`:

```ini
[Unit]
Description=HR RAG 예약 업로드 처리 워커
After=network.target

[Service]
Type=simple
User=hrrag
WorkingDirectory=/opt/data-gov
Environment=PYTHONUNBUFFERED=1
ExecStart=/opt/data-gov/.venv/bin/python -m scripts.ingest_worker
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now hr-ingest-worker
sudo systemctl status hr-ingest-worker      # 상태 확인
journalctl -u hr-ingest-worker -f           # 처리 로그 보기
```

워커는 처리 시간대 밖에는 5분마다 한 번씩 깨어나 확인만 하고 다시 잡니다. CPU·GPU 를
쓰지 않습니다.

### 워커가 살아 있는지 화면에서 보입니다

워커는 루프를 돌 때마다 `UPLOAD_QUEUE_DIR/.worker-heartbeat` 에 시각을 남깁니다.
이 신호가 **15분 넘게 없으면** 문서 관리 화면의 예약 현황에 빨간 경고가 뜹니다:

> ⛔ **처리 워커가 돌고 있지 않습니다.** … 예약한 문서는 처리되지 않고 계속 대기합니다.

이 경고가 없는데도 문서가 계속 `대기 중`이면 아직 **예약 시각이 안 됐거나** 처리
시간대(기본 18:00~08:00) 밖입니다.

### `대기 중`에서 안 넘어갈 때 — 진단 스크립트

```bash
python -m scripts.check_queue
```

- 워커가 살아 있는지(마지막 신호가 몇 분 전인지)
- 지금이 처리 시간대 안인지
- 대기·처리중·완료·실패 건수
- 대기 중인 각 건의 **예약 시각(KST)** 과 지금 집을 수 있는 건수
- 마지막에 **원인 추정**("워커가 안 떠 있습니다" / "아직 예약 시각 전입니다" / "시간대
  밖입니다")

를 한 번에 보여줍니다. 대부분은 워커가 안 떠 있는 경우입니다
(`sudo systemctl status hr-ingest-worker`).

## 설정 (.env)

```ini
UPLOAD_QUEUE_DIR=./storage/_queue    # 예약된 파일이 잠시 머무는 곳
SCHEDULE_TIMEZONE=Asia/Seoul         # 처리 시각 해석 기준(⚠️ 아래 설명)
INGEST_WINDOW_START=18:00            # 처리 시작
INGEST_WINDOW_END=08:00              # 처리 종료(시작>종료면 자정을 넘김)
INGEST_WORKERS=4                     # 동시 처리 수
UPLOAD_BATCH_FILES=20                # 한 묶음 최대 파일 수
UPLOAD_BATCH_MB=50                   # 한 묶음 최대 크기(둘 중 먼저 걸리는 쪽)
UPLOAD_MAX_TOTAL_MB=2048             # 한 번에 예약 가능한 총 용량
```

⚠️ **`SCHEDULE_TIMEZONE` 은 반드시 맞춰 두세요.** 서버 시스템 시계가 UTC 인 경우가 흔한데,
그러면 "18:00" 이 18:00 UTC = **새벽 3시 KST** 로 해석됩니다. 18:00~08:00 설정이
KST 03:00~17:00 이 되어 정확히 업무시간에 GPU 를 쓰게 됩니다. 이 값을 두면 서버 시계가
무엇이든 여기 적힌 시간대로 계산합니다(Django `TIME_ZONE` 은 워커에 영향이 없습니다).

- 업무 시간에 GPU 를 점유하면 채팅 응답이 느려지므로 기본을 저녁~아침으로 뒀습니다.
- 24시간 처리하려면 시작·종료를 같은 값으로 두면 됩니다(`00:00`/`00:00`).
- 동시 처리 수는 vLLM 이 배치로 묶어 처리하므로 4~8 정도가 무난합니다. 너무 올리면 채팅과
  GPU 를 다투게 됩니다.

웹 쪽 개수 한도는 `web/hrrag/settings.py` 에 있습니다.

```python
UPLOAD_WARN_FILES = 20              # 즉시 처리에서 이보다 많으면 화면 경고
UPLOAD_SYNC_MAX_FILES = 50          # 즉시 처리 한도
DATA_UPLOAD_MAX_NUMBER_FILES = 500  # 한 요청의 하드 한도(예약은 나눠 보내므로 안 걸림)
FILE_UPLOAD_MAX_MEMORY_SIZE = 512 * 1024   # 이보다 큰 파일은 메모리 대신 임시파일로
```

`FILE_UPLOAD_MAX_MEMORY_SIZE` 는 Django 기본이 2.5MB 입니다. 그대로 두면 2.4MB 짜리
파일 여러 개가 한 요청에 올 때 그만큼이 **통째로 RAM 에** 올라갑니다. 예약 업로드는
받자마자 디스크에 쓰므로 메모리에 들고 있을 이유가 없어 낮게 잡았습니다.

## 동작 정리

```
[브라우저] 파일 200개 + 폴더 선택
    └─ POST /console/docs/ (mode=queue)
         └─ storage/_queue/<배치>/0000/원본이름.docx  … 파일만 저장
         └─ upload_jobs 테이블에 200행(queued)         … 수 초 만에 응답
                                   ↓
[워커] 18:00 이후 — 한 건씩 원자적으로 선점(queued→processing)
         └─ 파싱 → AI 자동 채움 → 검토 생략 등록(폴더 권한 그대로) → 색인
         └─ 성공: done + 대기 파일 삭제 / 실패: 최대 3회 재시도 후 failed
```

- **중복 방지**: 여러 워커를 띄워도 같은 건을 둘이 잡지 않습니다(PostgreSQL 은 `SKIP LOCKED`).
- **재시도**: 일시 오류는 최대 3회. 파일을 못 읽는 종류(형식 미지원 등)는 다시 해도 같으므로
  바로 실패로 마감합니다.
- **중복 문서**: 이미 같은 내용이 등록돼 있으면 실패가 아니라 **건너뜀**으로 처리합니다.
- **워커가 죽었을 때**: `processing` 상태로 30분 넘게 멈춰 있으면 다시 대기열로 돌립니다.

### 시간대가 끝날 때까지 안 끝나면 (08:00)

**멈췄다가 다음 시간대에 이어서 합니다.**

- 08:00 이 되면 **새 문서를 더 집지 않습니다.** 이미 손댄 문서만 마치고 멈춥니다.
- 문서는 한 건씩 커밋되므로 **그때까지 등록한 것은 그대로 남습니다.**
- 남은 것은 대기열에 그대로 있다가 다음 18:00 부터 이어서 처리됩니다.
- 화면 현황에 "대기 N건"으로 남아 있어 얼마나 남았는지 보입니다.

```
18:00  600건 처리 시작
08:00  420건 등록 완료 → 멈춤 (남은 180건은 대기)
18:00  180건부터 이어서 처리
```

로그에도 남습니다: `08:00 이 되어 멈춥니다 — 남은 180건은 18:00 부터 이어서 처리합니다.`

## 서버 일괄 반입과 뭐가 다른가

| | 웹 예약 업로드 | 서버 일괄 반입(`scripts.bulk_ingest`) |
|---|---|---|
| 파일 전달 | 브라우저에서 업로드 | 서버 디렉터리에 미리 복사(Samba 등) |
| 폴더 → 권한 | 화면에서 **하나** 고름 | 디렉터리 구조를 조직도에 자동 매칭 |
| 적정 규모 | 수백 건 | 수천~만 건 |
| 필요 권한 | 일반 사용자 | 서버 접속 |

여러 부서의 문서를 한꺼번에 넣는 최초 이관은 서버 일괄 반입이 맞고(`docs/일괄반입.md`),
평소 한 부서에서 수십~수백 건을 올리는 건 웹 예약 업로드가 편합니다.
