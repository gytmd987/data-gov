# 질문 이해 — 판단 루프와 스트리밍

## 무엇이 문제였나

예전 채팅은 경로가 하나로 고정돼 있었습니다.

```
질문 → 의미 검색 1회 → 비슷한 조각 6개 → 답변
```

그래서 이런 질문이 구조적으로 안 됐습니다.

| 질문 | 왜 안 됐나 |
|---|---|
| "최근 그룹장한테 보고한 문서가 뭐야?" | 조건(작성자·보고선·기간)으로 **거르는** 일인데 의미 유사도만 봤습니다. "그룹장", "보고" 가 본문에 들어 있는 옛날 메일이 이겼습니다 |
| "이 법이 바뀌었는데 영향받는 규정 다 찾아줘" | **빠짐없이 훑어야** 하는 일인데 상위 6개만 봤습니다 |
| "우리 부서 규정이 몇 개야?" | 세는 일인데 셀 방법이 없었습니다 |

질문 종류마다 코드를 다는 방식은 새 질문이 나올 때마다 개발이 필요합니다. 그래서
**LLM 에게 도구를 주고 계획은 LLM 이 짜게** 바꿨습니다.

## 지금 어떻게 도나

```
질문 → (의미 검색을 미리 한 번 돌려 둠) → LLM 판단 → 도구 실행 → 다시 판단 → … → 답변
```

LLM 이 고를 수 있는 도구는 넷입니다.

| 도구 | 하는 일 | 언제 |
|---|---|---|
| `문서_세기` | 조건에 맞는 문서가 몇 건인지 | 전수로 훑을지 좁힐지 **먼저 규모를 잴 때** |
| `문서_목록` | 조건으로 목록 뽑기 | **빠짐없이 봐야 할 때**(의미 검색은 상위 몇 개만 줍니다) |
| `내용_검색` | 의미로 본문 조각 찾기 | 내용을 묻는 질문 |
| `문서_읽기` | 특정 문서를 자세히 | 목록에서 고른 것을 하나씩 확인할 때 |

`app/search/agent.py`(판단 루프) · `app/search/tools.py`(도구) · `app/search/pipeline.py`
(`answer_events`) 입니다.

### 예: "이 법이 바뀌었습니다. 영향받는 사내 규정 찾아 주세요"

```
1. 문서_세기(종류=규정)   → 47건. 전수로 볼 만하다고 판단
2. 문서_목록(종류=규정)   → 47건의 제목·요약
3. 요약을 보고 관련 있어 보이는 12건 추림
4. 문서_읽기 × 12         → 조항별로 영향 여부 판단
5. 근거와 함께 정리
```

규정이 그 법을 인용하지 않아도 됩니다. **내용을 보고 판단**하기 때문입니다.

### 예: "연차 며칠이야?"

미리 돌려 둔 검색 결과로 **첫 판단에서 바로 답합니다.** 도구를 더 부르지 않습니다.

## 첫 검색을 미리 돌리는 이유

흔한 질문은 예전 방식의 검색 한 번이면 충분합니다. 그걸 LLM 에게 물어보고 나서
검색하면 왕복이 하나 더 늘어 그만큼 느려집니다. 미리 돌려서 **근거와 함께** 물어보면
대부분 첫 판단에서 끝나고, 추가 비용은 짧은 판단 호출 하나뿐입니다.

| 질문 | 예전 | 지금 |
|---|---|---|
| "연차 며칠이야?" | 4~9초 | 5~10초 (판단 1회 추가) |
| "그룹장한테 보고한 문서" | 4~9초 — 틀린 답 | 5~10초 — 도구 1번 |
| 법령 영향도 | 4~9초 — 틀린 답 | 몇 분 (원래 그만한 일) |

## 스트리밍

예전에는 답변을 **다 만든 뒤** 한 번에 보냈습니다. 4~9초 동안 화면이 멈춘 것처럼
보였습니다. 지금은 도착하는 대로 흘려보냅니다.

- 진행 상황이 한 줄씩 쌓입니다 — `문서 47건 확인` → `목록 12건` → `'출장비 규정' 읽음`
- 답변은 첫 글자부터 나옵니다
- 다 끝나면 **최종본으로 한 번 갈아 끼웁니다** — 인용 번호 정리·한자 제거·출처 목록이
  이때 붙습니다

`POST /chat/stream` (SSE) 이고, 이벤트는 `step` · `delta` · `done` · `error` 입니다.
`POST /chat/send` 는 그대로 남아 있습니다(한 번에 JSON). **둘 다 같은 함수를 씁니다**
(`web/chat/views.py::run_turn`) — 경로를 나눠 두면 한쪽만 고쳐져 조용히 어긋납니다.

## 권한 — 구조로 막습니다

LLM 이 검색 조건을 만든다고 해서 권한까지 만들게 하면 안 됩니다.

- 도구는 **사용자를 인자로 받지 않습니다.** 호출하는 쪽(`ToolBox`)이 붙입니다
- LLM 이 낸 조건은 **AND 로만** 붙습니다 — 좁히기만 하고 넓히지 못합니다
- LLM 에게 열람 토큰을 **보여주지 않습니다** — 프롬프트로 우회할 대상이 없습니다
- `문서_읽기` 는 본문을 주기 전에 채팅 검색과 **똑같은 규칙**으로 다시 확인합니다
- 답변에 넣기 직전 한 번 더 거릅니다
- 모르는 문서 종류 같은 값은 **버립니다**(거르지 않느니만 못합니다)

감사로그에는 최종 질문만이 아니라 **도구 호출 내역**도 남습니다(`tool_calls`).

## 안 되면 어떻게 되나

새 기능 때문에 답이 아예 안 나오는 일은 없어야 합니다.

| 상황 | 결과 |
|---|---|
| 판단 LLM 이 죽음 | 미리 돌려 둔 검색 결과로 답합니다 = 예전 동작 |
| 도구 하나가 죽음 | 오류를 LLM 에게 돌려주고 루프는 계속됩니다 |
| 같은 호출을 반복 | 진전이 없다고 보고 멈춥니다 |
| 8걸음을 넘김 | 그때까지 모은 근거로 답합니다 |
| 모르는 도구 이름 | 아무것도 실행하지 않고 답변으로 넘어갑니다 |

## 끄는 법

채팅 화면의 **`자세히 찾기`** 토글입니다. 끄면 판단 루프 없이 예전 경로(검색 1회)로
갑니다. 스트리밍은 켜진 채로 남습니다.

## 느릴 때 — 어디서 시간이 가는지부터 재세요

```bash
python -m scripts.bench_chat "연차는 며칠인가요?" --user 내이메일@회사.com
python -m scripts.bench_chat "..." --user ... --plan     # 판단 루프까지 포함
```

단계별 초와 **첫 글자까지 걸린 시간(TTFT)** 을 보여 줍니다. 사람이 느끼는 지연은 총
시간보다 TTFT 에 가깝습니다.

### 대개 이 셋입니다

**1. 표(엑셀·워드 표) 청크가 통째로 들어간다 — 실제로 제일 컸습니다**

표는 헤더를 지키려고 **쪼개지 않고 한 청크**로 둡니다(`chunking.py`). 그래서 청크
하나가 수만 자가 되기도 합니다. 그게 그대로:

- 리랭커에 후보 24~40개로 들어갑니다 → **리랭킹이 8초 넘게** 걸립니다
- 답변 프롬프트에 6~14개 들어갑니다 → **첫 글자까지 6초**가 걸립니다

관련도 판단이나 답변에는 앞부분이면 충분하므로 **보낼 때만** 자릅니다.
저장된 원문·화면 인용문·다운로드는 그대로입니다.

```ini
RERANK_TOP_N=24         # 리랭커 후보 수(예전 40). 후보 수에 거의 비례해 느려집니다
RERANK_MAX_CHARS=1200   # 리랭커에 보낼 청크당 글자 수
ANSWER_MAX_CHARS=2500   # 답변 프롬프트에 넣을 청크당 글자 수
ANSWER_TOTAL_CHARS=20000  # 프롬프트 전체 상한
```

> 전체 상한이 없으면 판단 루프가 근거를 14개까지 모았을 때 vLLM 의
> `--max-model-len` 을 넘어 **답이 아예 안 나옵니다.**

**1-1. 리랭커가 CPU 로 돌고 있다**

```bash
python -m scripts.check_tei     # GPU 로 도는지 재 본다
```

CPU 면 후보 24개에 **8초쯤** 걸립니다. 이건 리랭커 고장이 아니라 **원래 그만큼 무거운
작업**입니다. 임베딩과 비교하면 분명합니다 — 두 모델은 **크기가 같은데(568M)** 처리량이
다릅니다.

| | 무엇을 처리하나 | 토큰 수 | CPU 소요 |
|---|---|---|---|
| 임베딩 | 질문 **한 줄** | ~15 | 0.1초 |
| 리랭커 | 후보 문서 24개 **전문** × 질문 | ~17,000 | 8초 |

문서 임베딩은 **적재할 때 이미 해 뒀으므로** 질문할 때는 질문 한 줄만 벡터로 바꿉니다.
반면 리랭커는 크로스 인코더라 (질문+문서) 쌍마다 모델을 처음부터 다시 돌립니다.
약 1,000배입니다.

### GPU 를 못 쓸 때 — 끄기 전에 줄이세요

비용은 `후보 수 × 글자 수` 에 거의 비례하므로 둘 다 줄이면 곱으로 줄어듭니다.

```ini
RERANK_TOP_N=8        # 24 → 8    (3배)
RERANK_MAX_CHARS=600  # 1200 → 600 (2배)
```

→ 대략 **8초 → 1~1.5초**.

품질 손실은 생각보다 작습니다. 하이브리드 검색(의미+BM25)을 RRF 로 융합해 이미 쓸 만한
순위를 만들어 두었고, 리랭커는 **그 상위 몇 개를 다시 줄 세우는 역할**입니다. 24개를
재정렬하나 8개를 재정렬하나 최종 6개를 뽑는 결과는 거의 같습니다.

그래도 느리면 아예 끕니다:

```ini
RERANK_ENABLED=false   # 8초 → 0초. 검색 융합 순위를 그대로 사용
```

껐을 때 품질이 실제로 떨어지는지는 **느낌이 아니라 `app/eval/` 골든셋으로** 재세요.

> CPU 코어를 몇 개나 쓰는지도 확인해 보세요. `docker stats --no-stream reranker` 가
> 100% 근처면 1코어만 쓰는 중입니다 — 리랭커 서비스에 `OMP_NUM_THREADS`,
> `RAYON_NUM_THREADS` 를 코어 수에 맞춰 넣으면 그만큼 빨라집니다.

**2. 생성 길이에 상한이 없었다**

답변이 길어지는 만큼 그대로 기다립니다. 이제 상한이 있습니다.

```ini
VLLM_MAX_TOKENS=800        # 채팅 답변
VLLM_TASK_MAX_TOKENS=400   # 도구 선택·SQL 같은 기계용 짧은 응답
```

**2-1. 추론(`<think>`) — 모델에 따라 다릅니다**

Qwen3 계열은 추론이 기본으로 켜져 있어 짧은 질문에도 보이지 않는 토큰을 먼저
만듭니다. 다만 **모델이 이 옵션을 지원하지 않으면 켜고 꺼도 차이가 없습니다.**
한 번 재 보고 차이가 없으면 신경 쓰지 마세요.

```ini
VLLM_THINKING=answer   # 기본 — 답변에만 허용, 도구 선택·SQL 은 끔
VLLM_THINKING=off      # 지원하는 모델이면 제일 빠름
```

**3. 답변을 만들어 놓고 버렸다**

표(엑셀) 질문은 SQL 로 답하는데, 예전에는 **문장 답변을 다 만든 뒤** 표 답변으로
갈아 끼웠습니다. 생성 시간이 통째로 낭비였고, 화면에서도 답이 흘러나오다 전혀 다른
답으로 바뀌었습니다. 지금은 문장을 만들기 **전에** 판단해서 건너뜁니다.

### 그래도 상용 서비스만큼은 안 됩니다

27B 모델이 GPU 한 장에서 도는 구조라, 수천 장으로 서비스하는 곳과 같은 속도는 안
나옵니다. 다만 위 셋을 정리하면 **수십 초 → 한 자릿수 초**는 충분히 가능합니다.
더 필요하면 더 작은 모델(7~14B)을 쓰는 게 가장 확실한 방법입니다.

## 아직 부족한 것

- **판단이 틀리면 그럴듯하게 틀립니다.** 그래서 진행 상황을 화면에 드러냅니다 —
  무엇을 뒤졌는지 보이면 사람이 알아챌 수 있습니다
- **문서가 아주 많으면 전수 검토를 못 합니다.** `문서_세기` 로 먼저 규모를 재고,
  너무 많으면 범위를 좁혀 달라고 답하게 돼 있습니다
- 로컬 모델(27B)이 계획을 얼마나 잘 짜는지는 **실제로 써 보며 재야 합니다.**
  `app/eval/` 골든셋에 잘 안 되는 질문을 모아 두고 hit@3 대신 **재현율**로 보세요
