# 질문 이해 — 판단 루프와 스트리밍

## 무엇이 문제였나

예전 채팅은 경로가 하나로 고정돼 있었습니다.

```
질문 → 의미 검색 1회 → 비슷한 조각 6개 → 답변
```

그래서 이런 질문이 구조적으로 안 됐습니다.

| 질문 | 왜 안 됐나 |
|---|---|
| "최근 그룹장한테 보고한 문서가 뭐야?" | 조건(작성자·보고선·기간)으로 **거르는** 일인데 의미 유사도만 봤습니다. "그룹장", "보고" 가 본문에 들어 있는 옛날 메일이 이겼습니다 |
| "이 법이 바뀌었는데 영향받는 규정 다 찾아줘" | **빠짐없이 훑어야** 하는 일인데 상위 6개만 봤습니다 |
| "우리 부서 규정이 몇 개야?" | 세는 일인데 셀 방법이 없었습니다 |

질문 종류마다 코드를 다는 방식은 새 질문이 나올 때마다 개발이 필요합니다. 그래서
**LLM 에게 도구를 주고 계획은 LLM 이 짜게** 바꿨습니다.

## 지금 어떻게 도나

```
질문 → (의미 검색을 미리 한 번 돌려 둠) → LLM 판단 → 도구 실행 → 다시 판단 → … → 답변
```

LLM 이 고를 수 있는 도구는 넷입니다.

| 도구 | 하는 일 | 언제 |
|---|---|---|
| `문서_세기` | 조건에 맞는 문서가 몇 건인지 | 전수로 훑을지 좁힐지 **먼저 규모를 잴 때** |
| `문서_목록` | 조건으로 목록 뽑기 | **빠짐없이 봐야 할 때**(의미 검색은 상위 몇 개만 줍니다) |
| `내용_검색` | 의미로 본문 조각 찾기 | 내용을 묻는 질문 |
| `문서_읽기` | 특정 문서를 자세히 | 목록에서 고른 것을 하나씩 확인할 때 |

`app/search/agent.py`(판단 루프) · `app/search/tools.py`(도구) · `app/search/pipeline.py`
(`answer_events`) 입니다.

### 예: "이 법이 바뀌었습니다. 영향받는 사내 규정 찾아 주세요"

```
1. 문서_세기(종류=규정)   → 47건. 전수로 볼 만하다고 판단
2. 문서_목록(종류=규정)   → 47건의 제목·요약
3. 요약을 보고 관련 있어 보이는 12건 추림
4. 문서_읽기 × 12         → 조항별로 영향 여부 판단
5. 근거와 함께 정리
```

규정이 그 법을 인용하지 않아도 됩니다. **내용을 보고 판단**하기 때문입니다.

### 예: "연차 며칠이야?"

미리 돌려 둔 검색 결과로 **첫 판단에서 바로 답합니다.** 도구를 더 부르지 않습니다.

## 첫 검색을 미리 돌리는 이유

흔한 질문은 예전 방식의 검색 한 번이면 충분합니다. 그걸 LLM 에게 물어보고 나서
검색하면 왕복이 하나 더 늘어 그만큼 느려집니다. 미리 돌려서 **근거와 함께** 물어보면
대부분 첫 판단에서 끝나고, 추가 비용은 짧은 판단 호출 하나뿐입니다.

| 질문 | 예전 | 지금 |
|---|---|---|
| "연차 며칠이야?" | 4~9초 | 5~10초 (판단 1회 추가) |
| "그룹장한테 보고한 문서" | 4~9초 — 틀린 답 | 5~10초 — 도구 1번 |
| 법령 영향도 | 4~9초 — 틀린 답 | 몇 분 (원래 그만한 일) |

## 스트리밍

예전에는 답변을 **다 만든 뒤** 한 번에 보냈습니다. 4~9초 동안 화면이 멈춘 것처럼
보였습니다. 지금은 도착하는 대로 흘려보냅니다.

- 진행 상황이 한 줄씩 쌓입니다 — `문서 47건 확인` → `목록 12건` → `'출장비 규정' 읽음`
- 답변은 첫 글자부터 나옵니다
- 다 끝나면 **최종본으로 한 번 갈아 끼웁니다** — 인용 번호 정리·한자 제거·출처 목록이
  이때 붙습니다

`POST /chat/stream` (SSE) 이고, 이벤트는 `step` · `delta` · `done` · `error` 입니다.
`POST /chat/send` 는 그대로 남아 있습니다(한 번에 JSON). **둘 다 같은 함수를 씁니다**
(`web/chat/views.py::run_turn`) — 경로를 나눠 두면 한쪽만 고쳐져 조용히 어긋납니다.

## 권한 — 구조로 막습니다

LLM 이 검색 조건을 만든다고 해서 권한까지 만들게 하면 안 됩니다.

- 도구는 **사용자를 인자로 받지 않습니다.** 호출하는 쪽(`ToolBox`)이 붙입니다
- LLM 이 낸 조건은 **AND 로만** 붙습니다 — 좁히기만 하고 넓히지 못합니다
- LLM 에게 열람 토큰을 **보여주지 않습니다** — 프롬프트로 우회할 대상이 없습니다
- `문서_읽기` 는 본문을 주기 전에 채팅 검색과 **똑같은 규칙**으로 다시 확인합니다
- 답변에 넣기 직전 한 번 더 거릅니다
- 모르는 문서 종류 같은 값은 **버립니다**(거르지 않느니만 못합니다)

감사로그에는 최종 질문만이 아니라 **도구 호출 내역**도 남습니다(`tool_calls`).

## 안 되면 어떻게 되나

새 기능 때문에 답이 아예 안 나오는 일은 없어야 합니다.

| 상황 | 결과 |
|---|---|
| 판단 LLM 이 죽음 | 미리 돌려 둔 검색 결과로 답합니다 = 예전 동작 |
| 도구 하나가 죽음 | 오류를 LLM 에게 돌려주고 루프는 계속됩니다 |
| 같은 호출을 반복 | 진전이 없다고 보고 멈춥니다 |
| 8걸음을 넘김 | 그때까지 모은 근거로 답합니다 |
| 모르는 도구 이름 | 아무것도 실행하지 않고 답변으로 넘어갑니다 |

## 끄는 법

채팅 화면의 **`자세히 찾기`** 토글입니다. 끄면 판단 루프 없이 예전 경로(검색 1회)로
갑니다. 스트리밍은 켜진 채로 남습니다.

## 아직 부족한 것

- **판단이 틀리면 그럴듯하게 틀립니다.** 그래서 진행 상황을 화면에 드러냅니다 —
  무엇을 뒤졌는지 보이면 사람이 알아챌 수 있습니다
- **문서가 아주 많으면 전수 검토를 못 합니다.** `문서_세기` 로 먼저 규모를 재고,
  너무 많으면 범위를 좁혀 달라고 답하게 돼 있습니다
- 로컬 모델(27B)이 계획을 얼마나 잘 짜는지는 **실제로 써 보며 재야 합니다.**
  `app/eval/` 골든셋에 잘 안 되는 질문을 모아 두고 hit@3 대신 **재현율**로 보세요
