# 서버 기초 — 도커·PostgreSQL·Qdrant가 뭔지, 팀원과 같이 쓰려면

용어를 하나도 모른다는 전제로 씁니다.

---

## 0. 결론부터 — 팀원은 아무것도 설치하지 않습니다

**PostgreSQL·Qdrant는 팀원이 쓰는 프로그램이 아닙니다.** 자동차 엔진 부품 같은 것이라,
운전자(팀원)는 존재조차 몰라도 됩니다.

```
팀원이 하는 일 : 브라우저 열고 → http://서버주소:8500 → 로그인 → 끝
관리자가 하는 일: 서버에서 부품들을 켜 두고, 팀원 계정을 만들어 주는 것
```

팀원 PC 에는 **설치할 것이 없습니다.** 사내망에 연결된 PC 와 브라우저(크롬/엣지)만 있으면
됩니다. 필요한 건 딱 두 가지입니다.

1. 서버 주소 (예: `http://10.1.2.3:8500`)
2. 계정 (아이디=이메일, 비밀번호) ← 관리자가 만들어 줌

## 1. 이 시스템은 어떤 부품들로 되어 있나

식당에 비유하면 이렇습니다.

| 부품 | 식당으로 치면 | 하는 일 | 팀원이 알아야 하나 |
|---|---|---|---|
| **Django 웹** | 홀·메뉴판 | 팀원이 보는 화면 전부 | 주소만 알면 됨 |
| **PostgreSQL** | 장부 | 문서 정보·계정·권한·조직도 기록 | ❌ |
| **Qdrant** | 색인 카드함 | "비슷한 내용" 을 찾아내는 검색 저장소 | ❌ |
| **TEI (임베딩)** | 번역기 | 문장을 숫자로 바꿈(검색용) | ❌ |
| **vLLM** | 요리사 | 답변 문장을 만들어 냄 | ❌ |

### PostgreSQL (줄여서 '포스트그레스')

**데이터베이스**입니다. 엑셀 파일을 아주 튼튼하게 만든 것이라고 생각하면 됩니다.
"누가 어떤 문서를 언제 올렸고, 누가 볼 수 있는지" 같은 **표로 정리되는 정보**를 담습니다.

엑셀과 다른 점은, 여러 사람이 동시에 고쳐도 안 깨지고 갑자기 정전이 나도 내용이 안
날아간다는 것입니다.

### Qdrant (큐드런트)

**벡터 데이터베이스**입니다. 이게 이 시스템의 핵심입니다.

일반 검색은 글자가 똑같아야 찾습니다. "연차"로 검색하면 "연차"가 적힌 문서만 나옵니다.
그런데 사용자는 "휴가 며칠 쓸 수 있어?"라고 묻습니다. 문서에는 "연차 15일"이라고만
적혀 있고 "휴가 며칠"이라는 말은 없습니다.

Qdrant 는 **뜻이 비슷한 것**을 찾습니다. 문장을 숫자 묶음(벡터)으로 바꿔서 저장해 두고,
질문도 숫자로 바꿔서 "숫자가 가까운 것"을 찾는 방식입니다. 그래서 "휴가"로 물어도
"연차" 문서를 찾아냅니다.

> 문서 원본 파일은 Qdrant 가 아니라 **서버 디스크**(`storage/originals/`)에 조직도 모양
> 그대로 저장됩니다. Qdrant 에는 검색용 숫자만 들어갑니다.

### MinIO — 지금은 안 씁니다

`docker-compose.yml` 에 들어 있지만 **현재 코드에서 사용하지 않습니다**(원본 파일은 서버
디스크에 직접 저장). 나중에 파일 저장소를 분리할 때를 대비해 남겨둔 것이니, 지금은
꺼 두어도 됩니다.

## 2. 도커(Docker)가 뭔가

### 문제

PostgreSQL 을 서버에 직접 설치한다고 해봅시다. 그러면 이런 일이 생깁니다.

- "리눅스 버전이 안 맞아서 설치가 안 됩니다"
- "다른 프로그램이 쓰는 라이브러리랑 충돌합니다"
- "지웠는데 찌꺼기가 남아서 재설치가 안 됩니다"

프로그램 하나 깔았다가 서버 전체가 꼬이는 일이 흔합니다.

### 해결

도커는 **프로그램 + 그게 필요로 하는 모든 것을 상자 하나에 담아** 통째로 실행합니다.
상자 안은 바깥과 격리돼 있어서, 상자를 지우면 흔적 없이 사라집니다. 서버에는 도커
하나만 설치하고, 나머지는 전부 상자로 돌리는 방식입니다.

### 용어 세 개만 알면 됩니다

| 용어 | 뜻 | 비유 |
|---|---|---|
| **이미지(image)** | 프로그램 설계도 | 붕어빵 **틀** |
| **컨테이너(container)** | 실행 중인 상자 | 틀로 구워낸 **붕어빵** |
| **볼륨(volume)** | 데이터를 담아 두는 창고 | 붕어빵과 **따로 보관한 팥** |

**볼륨이 제일 중요합니다.** 컨테이너는 지웠다 다시 만들어도 되지만, 볼륨을 지우면
**데이터가 영구히 사라집니다.** 우리 설정에는 세 개가 있습니다.

```yaml
volumes:
  pgdata:      # PostgreSQL 데이터 — 문서 정보, 계정, 권한 전부
  qdrantdata:  # Qdrant 데이터 — 검색 색인
  hf_cache:    # AI 모델 파일 (다시 받으면 되므로 덜 중요)
```

> ⚠️ `docker compose down -v` 의 **`-v` 는 볼륨까지 지웁니다.** 이 명령은 "전부 초기화"를
> 뜻합니다. 절대 습관적으로 치지 마세요. 평소 정지는 `-v` 없이 `docker compose down`.

### compose 는 또 뭔가

부품이 5개면 상자를 5번 띄워야 합니다. 그걸 **한 파일에 적어 두고 명령 한 줄로** 다
띄우는 게 도커 컴포즈(compose)입니다. 그 파일이 `docker-compose.yml` 입니다.

## 3. 서버에서 실제로 하는 일

프로젝트 폴더로 이동한 뒤 실행합니다.

```bash
cd /opt/data-gov          # 프로젝트를 둔 경로
```

### 켜기

```bash
docker compose up -d
```

- `up` = 띄워라, `-d` = 백그라운드로(터미널을 닫아도 계속 돎)
- 처음 실행하면 이미지를 받느라 몇 분 걸립니다. 두 번째부터는 몇 초입니다.

### 상태 보기

```bash
docker compose ps
```

```
NAME                  IMAGE                 STATUS
data-gov-postgres-1   postgres:16           Up 2 hours
data-gov-qdrant-1     qdrant/qdrant:latest  Up 2 hours
```

`Up` 이면 정상입니다. `Exited` 나 `Restarting` 이면 문제가 있는 것이니 로그를 봅니다.

### 로그 보기 (문제가 생겼을 때)

```bash
docker compose logs postgres        # 특정 부품
docker compose logs -f --tail 50    # 전체, 실시간으로 계속
```

`-f` 는 계속 지켜보기입니다. 빠져나올 때는 `Ctrl+C`.

### 끄기 / 재시작

```bash
docker compose stop                 # 잠깐 멈춤 (데이터 그대로)
docker compose start                # 다시 시작
docker compose restart qdrant       # 하나만 재시작
docker compose down                 # 컨테이너 삭제 (⚠️ 볼륨은 유지되니 데이터는 안전)
```

### 잘 붙었는지 한 번에 확인

```bash
python -m scripts.preflight
```

Postgres·Qdrant·임베딩·vLLM 을 하나씩 찔러 보고 **어디가 막혔는지 콕 집어** 알려줍니다.
"뭔가 안 되는데 원인을 모르겠다" 싶으면 이걸 먼저 돌리세요.

### 웹 화면 띄우기

도커로 부품을 켠 다음, 웹 앱을 따로 띄웁니다.

```bash
python web/manage.py runserver 0.0.0.0:8500
```

`0.0.0.0` 이 중요합니다. 이게 "다른 PC 에서도 접속 허용"이라는 뜻입니다.
`127.0.0.1` 로 띄우면 **서버 자기 자신에서만** 접속됩니다.

## 4. 팀원이 쓸 수 있게 하는 절차

### 4-1. 서버 주소 확인

```bash
hostname -I
```

나온 주소 중 사내망 대역(보통 `10.` 또는 `192.168.` 로 시작)을 씁니다.

### 4-2. 방화벽에서 **8500 포트만** 엽니다

```bash
sudo ufw allow 8500/tcp
sudo ufw status
```

> ⚠️ **PostgreSQL(5432)·Qdrant(6333) 포트는 절대 열지 마세요.** 팀원이 쓸 일이 없고,
> 열면 사내망 누구나 문서 데이터베이스에 직접 접근할 수 있습니다. 권한 설정을 아무리
> 잘해 놔도 그 뒷문으로 다 새어 나갑니다. 자세한 건 아래 5-3.

### 4-3. 팀원 계정 만들기

```bash
python web/manage.py createsuperuser      # 관리자용
```

일반 팀원 계정은 **웹 화면에서** 만드는 게 편합니다. 관리자로 로그인 → **사용자 관리**
→ 계정 추가 → 조직도에서 소속 부서 지정.

소속 부서가 곧 **볼 수 있는 문서 범위**이므로 정확히 지정해야 합니다.

### 4-4. 팀원에게 알려줄 것

> 주소: `http://10.1.2.3:8500`
> 아이디: 본인 회사 이메일
> 비밀번호: (처음 발급받은 것 → 로그인 후 우측 상단 **비밀번호** 에서 변경)

끝입니다. 설치할 것도, 알아야 할 용어도 없습니다.

## 5. ⚠️ 팀과 같이 쓰기 전에 바꿔야 할 것 3가지

혼자 테스트할 때는 괜찮았지만, **여러 명이 쓰는 순간 문제가 되는** 설정들입니다.

### 5-1. DEBUG 를 꺼야 합니다 (보안)

지금은 켜져 있습니다(`DJANGO_DEBUG` 기본값 `1`). 이 상태에서 오류가 나면 **에러 화면에
소스 코드와 설정값이 그대로 표시됩니다.** DB 비밀번호가 화면에 찍힐 수 있습니다.

`.env` 에 추가하세요.

```ini
DJANGO_DEBUG=0
DJANGO_SECRET_KEY=길고-아무도-모르는-값으로-바꾸세요
DJANGO_ALLOWED_HOSTS=10.1.2.3,localhost
```

`DJANGO_SECRET_KEY` 도 지금은 개발용 기본값입니다. 이 값을 아는 사람은 **남의 계정으로
로그인한 것처럼 위조**할 수 있습니다. 아래로 만드세요.

```bash
python -c "import secrets; print(secrets.token_urlsafe(50))"
```

> ⚠️ **여기서 거의 다 한 번씩 막힙니다.** `DJANGO_DEBUG=0` 으로 바꾸는 순간
> `DJANGO_ALLOWED_HOSTS` 가 **엄격하게** 적용됩니다. 팀원이 주소창에 치는 값이 목록에
> 없으면 화면이 통째로 **"Bad Request (400)"** 만 뜨고, 아무 설명도 안 나옵니다.
> 실제로 재현해 확인했습니다.
>
> ```
> ALLOWED_HOSTS=localhost      → http://127.0.0.1:8500 접속 시 HTTP 400
> ALLOWED_HOSTS=127.0.0.1,...  → HTTP 200 정상
> ```
>
> 팀원이 IP 로 접속하면 **그 IP 를 반드시 적어야** 합니다. 나중에 사내 도메인을 붙이면
> 그 도메인도 추가해야 합니다. 쉼표로 여러 개 적을 수 있습니다.

### 5-2. runserver 는 개발용입니다

`python web/manage.py runserver` 는 혼자 테스트할 때 쓰는 것입니다. 여러 명이 동시에
쓰면 느려지고, 오류가 나면 서버가 통째로 멈출 수 있습니다.

실서비스용으로 바꿉니다.

```bash
pip install gunicorn
gunicorn web.hrrag.wsgi:application --bind 0.0.0.0:8500 \
  --worker-class gthread --workers 4 --threads 8 --timeout 300
```

**프로젝트 폴더에서** 실행해야 합니다(`/opt/data-gov`). 실제로 띄워서 확인한 명령입니다.

- `--worker-class gthread --threads 8` : **채팅 답변을 흘려보내는 동안(스트리밍)
  연결이 계속 열려 있습니다.** 기본 방식(sync)이면 그 한 명이 일꾼 하나를 통째로
  붙잡아, 4명이 동시에 물으면 다섯 번째 사람은 기다립니다. 스레드를 쓰면 한 일꾼이
  여러 연결을 동시에 붙듭니다. 답변을 기다리는 시간은 GPU 가 일하는 시간이라 스레드로
  충분합니다.
- `--workers 4` : 프로세스 4개 (× 스레드 8 = 동시 32명분)
- `--timeout 300` : 즉시 업로드나 '자세히 찾기' 가 오래 걸려도 안 끊기게 (5분)

> 앞에 nginx 를 두었다면 `proxy_buffering off;` 를 채팅 경로에 걸어야 합니다.
> 버퍼링이 켜져 있으면 답변을 다 만들 때까지 붙들었다가 한 번에 내보내서
> 스트리밍이 무의미해집니다. (앱은 `X-Accel-Buffering: no` 를 이미 보냅니다.)

### 5-2-1. 명령을 외울 필요는 없습니다 — systemd 에 넣으세요

명령이 길어졌습니다. **한 번 등록해 두면 다시 칠 일이 없습니다.** 서버가 재부팅돼도,
프로세스가 죽어도 알아서 다시 뜹니다.

`/etc/systemd/system/hr-web.service`:

```ini
[Unit]
Description=HR RAG 웹
After=network.target

[Service]
Type=simple
User=hrrag
WorkingDirectory=/opt/data-gov
Environment=PYTHONUNBUFFERED=1
ExecStart=/opt/data-gov/.venv/bin/gunicorn web.hrrag.wsgi:application \
  --bind 0.0.0.0:8500 --worker-class gthread --workers 4 --threads 8 --timeout 300
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now hr-web        # 등록 + 지금 실행 (한 번만)
sudo systemctl status hr-web              # 잘 떠 있나
sudo systemctl restart hr-web             # 코드를 고친 뒤
journalctl -u hr-web -f                   # 로그 보기
```

### 5-2-2. 띄워야 하는 프로세스는 **둘**입니다

헷갈리기 쉬운 부분입니다. 이 시스템은 **항상 떠 있어야 하는 프로그램이 두 개**입니다.

| | 무엇 | 없으면 |
|---|---|---|
| **웹** (`hr-web`) | 사람이 보는 화면·채팅 | 사이트가 안 열립니다 |
| **워커** (`hr-ingest-worker`) | 예약 업로드 처리 | 화면은 멀쩡한데 **예약한 문서가 영원히 '대기 중'** |

둘 다 **같은 서버, 같은 폴더**(`/opt/data-gov`)에서 돕니다. 워커는 따로 어딘가에
접속해서 실행하는 게 아니라, 웹과 나란히 상주하는 프로그램입니다.

```bash
sudo systemctl enable --now hr-web hr-ingest-worker    # 둘 다 등록
sudo systemctl status hr-web hr-ingest-worker          # 둘 다 확인
```

워커 유닛 파일은 `docs/예약업로드.md` 에 있습니다. 워커가 안 떠 있으면 문서 관리
화면에 빨간 경고가 뜨므로 금방 알 수 있습니다.

### 5-3. DB 포트를 바깥에 열지 마세요

지금 `docker-compose.yml` 은 이렇게 돼 있습니다.

```yaml
ports:
  - "5432:5432"        # ← 서버의 모든 네트워크에서 접근 가능
```

앞에 `127.0.0.1:` 을 붙이면 **서버 자기 자신에서만** 접근하게 됩니다. 웹 앱은 같은
서버에서 도니 아무 문제가 없고, 바깥에서는 못 붙습니다.

```yaml
ports:
  - "127.0.0.1:5432:5432"
  - "127.0.0.1:6333:6333"
```

고친 뒤 `docker compose up -d` 를 다시 실행하면 반영됩니다.

## 6. 백업 — 이것만은 꼭

볼륨이 날아가면 **문서·계정·권한이 전부 사라집니다.** 원본 파일은 디스크에 남아 있어도
"누가 볼 수 있는지" 정보가 없어지므로 사실상 처음부터 다시 해야 합니다.

```bash
# PostgreSQL 백업 (하루 한 번 권장)
docker compose exec -T postgres pg_dump -U ragadmin ragdb > /backup/db_$(date +%F).sql

# 원본 파일 백업
tar czf /backup/files_$(date +%F).tar.gz storage/originals
```

되돌리기:

```bash
cat /backup/db_2026-08-07.sql | docker compose exec -T postgres psql -U ragadmin ragdb
```

> Qdrant(검색 색인)는 백업하지 않아도 됩니다. 날아가도
> `python -m scripts.reindex_search --recreate` 로 다시 만들 수 있습니다(시간은 걸립니다).

## 7. 자주 겪는 문제

| 증상 | 확인 | 해결 |
|---|---|---|
| 팀원이 접속이 안 됨 | 서버에서 `curl localhost:8500` | 되면 방화벽(4-2), 안 되면 웹 앱이 안 떠 있음 |
| **Bad Request (400)** 만 뜸 | `.env` 의 `DJANGO_ALLOWED_HOSTS` | 접속에 쓰는 IP·도메인을 추가(5-1) |
| "서버 오류" 화면 | `docker compose ps` | `Up` 아닌 것 재시작 |
| 검색은 되는데 답변이 이상 | `python -m scripts.preflight` | vLLM/TEI 연결 확인 |
| 문서를 올려도 검색에 안 나옴 | 검토 대기인지 확인 | 문서 화면에서 등록 확정 |
| 예약 업로드가 처리 안 됨 | `systemctl status hr-ingest-worker` | 워커가 안 떠 있음 |
| 시간이 이상함 | `python -m scripts.check_time` | `docs/예약업로드.md` 참고 |
| 서버 재부팅 후 다 죽음 | — | 도커는 `restart: unless-stopped` 라 자동 복귀. 웹 앱·워커는 systemd 등록 필요 |

## 8. 정리

```
[팀원 PC]  브라우저만 있으면 됨
    │  http://10.1.2.3:8500
    ▼
[서버] ─ 웹 앱 (gunicorn, 8500)          ← 유일하게 바깥에 여는 문
         │
         ├─ PostgreSQL (도커, 5432)      ┐
         ├─ Qdrant     (도커, 6333)      ├ 서버 안에서만 접근
         ├─ TEI 임베딩 (도커, 8081)      │
         └─ vLLM       (별도, 8000)      ┘
```

기억할 것은 세 가지입니다.

1. **팀원은 브라우저만 있으면 됩니다.** 설치할 게 없습니다.
2. **바깥에 여는 포트는 8500 하나뿐입니다.** 나머지는 서버 안에서만 씁니다.
3. **볼륨을 지우면 데이터가 사라집니다.** `docker compose down -v` 의 `-v` 를 조심하세요.
