# Django 웹앱 실행 가이드

ChatGPT 스타일 채팅(팀 데이터 기반 토글) + 관리 콘솔(문서 검토/관리/사용자 관리).
기존 Streamlit UI는 병행 유지 중이며, Django 검증 완료 후 삭제 예정.

## 1. 설치 & 실행

```bash
pip install -e ".[ingest,web,postgres]"
python web/manage.py migrate                 # Django auth 테이블 생성(기본 sqlite 파일)
python web/manage.py createsuperuser         # 관리자 계정 (username=이메일 권장)
python web/manage.py runserver 0.0.0.0:8500
```

브라우저: `http://서버주소:8500` → 로그인 → 채팅.

- 도메인 데이터(문서·권한·대화)는 기존 `.env`의 **Postgres/Qdrant/vLLM/TEI** 를 그대로 사용.
- 처음이면 `python -m scripts.migrate` 로 도메인 테이블도 갱신하세요(대화 테이블 포함).

## 2. 화면 구성

| 화면 | 경로 | 접근 |
|---|---|---|
| 💬 채팅 | `/` | 로그인한 모든 사용자 |
| 📤 문서 등록 | `/submit/` | 로그인한 모든 사용자 |
| 📄 문서 관리 | `/console/docs/` | 로그인한 모든 사용자(범위 제한) |
| 📝 문서 검토 | `/console/review/` | 관리자만 |
| 📨 요청 승인 | `/console/requests/` | 관리자·부서장 |
| 🏢 조직도 | `/console/org/` | 관리자만 |
| 👤 사용자 관리 | `/console/users/` | 관리자만 |

**관리자 판정**: Django 계정의 `is_staff` 이거나 `config/system.yaml`의 `permissions.admins` 이메일.
**부서장**: 조직도에서 팀장/그룹장/파트장 역할을 받은 사용자(자기 부서 subtree 관리).

## 3. 접근 통제(조직도 기반)

민감도 등급·PII는 사용하지 않습니다. 접근은 **조직도(People팀 > 그룹 > 파트)** 로만 통제합니다.
- 문서 접근 대상은 검토·관리 화면에서 노드별로 **부서 전체**(하위 전원+상위) 또는 **부서장만**(그 부서장+상위)을
  다중 선택합니다. 아무것도 안 고르면 **팀 전체 공개**입니다.
- 사용자는 조직도 노드+역할로 배정되며, 그 소속에 맞는 문서만 검색·열람합니다.

## 4. 채팅 사용법

- **[팀 데이터 기반 답변]** 토글: 켜면 사내 문서 근거+출처와 함께, 끄면 일반 멀티턴 답변.
- **[과거 문서 포함]** 토글: 켜면 만료·대체 문서까지 검색되고 출처에 **⚠️ 과거/만료 자료** 배지 표시.
  과거 포함이어도 **본인 조직 권한 검사는 그대로 적용**됩니다.
- 답변마다 👍/👎 피드백, 원본 다운로드는 **다운로드 시점에도 권한 재검증**.

## 5. 문서 등록·검토·요청 흐름

- **일반 사용자(파트원)**: `문서 등록`에서 자유롭게 업로드(검토 대기). `문서 관리`에서는 **자기 부서 문서를
  열람만** 하고, 수정·삭제는 **요청**으로 처리합니다.
- **부서장**: 자기 부서(하위 포함) 문서를 직접 수정·상태변경하고, 파트원 요청과 자기 부서 삭제 요청을 **승인**합니다.
- **관리자**: 전체 문서 관리 + 문서 검토(색인) + 조직도·사용자 관리 + 모든 요청 승인·영구 삭제.
- **AI 필수 항목**: 업로드 시 AI가 **요약·핵심 키워드·예상 Q&A**를 반드시 생성합니다. 생성 실패 시
  "내용 추출 실패(읽기 오류)"로 처리되어 등록이 거부됩니다(스캔 문서는 OCR 필요).
- **중복 처리**: 제목+형식이 같은 문서가 있으면 검토 화면에서 (이전 버전으로 교체 / 기존 삭제 요청 /
  별개 등록) 중 선택합니다. 삭제 승인 전까지 같은 제목 등록은 잠깁니다.

### 5-1. 대량 문서 관리 (수천~수만 건)

`문서 관리`(`/console/docs/`) 화면은 대량을 전제로 설계되어 있습니다:

- **페이징**: 한 페이지 50건씩 로드(전체를 한 번에 불러오지 않아 먹통 방지).
- **필터**: 파일명·제목 검색 + **상태**(사용 중/만료/보관/대체/초안) + **유형** 드롭다운.
- **일괄 작업**: 체크박스로 여러 건 선택 → 한 번에 상태 변경(예: 일괄 보관).
- **🧹 만료 문서 정리**: 만료일이 지난 문서를 즉시 만료 처리(아래 자동화의 수동 실행 버전).

### 5-2. 생애주기 자동화 (만료 자동 처리)

만료일(`expiry_date`)이 지난 문서를 `expired` 상태로 자동 전환하고 검색에서 제외합니다.

```bash
python -m scripts.lifecycle_sweep          # 만료 문서 일괄 정리(배치)
```

cron 등록(매일 새벽 3시) 예시:

```cron
0 3 * * *  cd /path/to/data-gov && python -m scripts.lifecycle_sweep >> /var/log/hrrag_sweep.log 2>&1
```

관리 화면 상단에는 **N일 이내 만료 예정** 건수가 표시되어 갱신 대상을 미리 알 수 있습니다.

## 6. 사용자·조직 등록 흐름

1. 관리자가 `조직도`에서 팀 > 그룹 > 파트 노드를 만듭니다(초기엔 비어 있음 — 임의 생성 안 함).
2. `사용자 관리`에서 **ID(이메일) + 소속 노드 + 역할(팀장/그룹장/파트장/파트원) + 초기 비밀번호** 입력 →
   조직 배정과 **로그인 계정이 함께 생성**됩니다.
3. 사용자는 그 이메일/비밀번호로 로그인 → 소속·역할에 맞는 문서만 검색·관리.

## 7. 서비스 없이 UI 확인 (오프라인 데모)

```bash
WEB_OFFLINE=1 python web/manage.py runserver 0.0.0.0:8500
```

vLLM/TEI/Qdrant/Postgres 없이 in-memory 가짜 컴포넌트로 전체 화면 흐름을 볼 수 있습니다.
자동 검증: `python -m scripts.web_smoke`

## 7-1. 업로드가 실패할 때

화면에 `⚠️ 파일명: …` 으로 **원인이 표시됩니다**. 그래도 모르겠으면 순서대로:

```bash
python -m scripts.check_services      # ① 필요한 것들이 다 떠 있나
journalctl -u hr-web -n 100           # ② 실패한 파일의 자세한 오류(스택트레이스)
```

`check_services` 는 문서 하나를 올릴 때 뒤에서 도는 것들을 순서대로 확인합니다.

```
파일 저장(디스크) → 파싱 → AI 자동채움(vLLM) → 임베딩(TEI) → 색인(Qdrant) → DB
```

### 화면에 뜨는 메시지별 조치

| 메시지 | 원인 | 조치 |
|---|---|---|
| `…에 연결하지 못했습니다` | 그 서비스가 안 떠 있음 | `docker compose ps` → `up -d` |
| `요청을 거절했습니다(400)` | 모델 설정 불일치 | `VLLM_MODEL` 이 `/v1/models` 의 id 와 같은지 |
| `모델을 찾지 못했습니다` | 모델 이름 오타 | 위와 같음 |
| `서버 디스크가 가득 찼습니다` | 디스크 부족 | `df -h` · 오래된 원본·대기 파일 정리 |
| `처리 시간이 초과됐습니다` | 서버가 바쁨 | 잠시 후 재시도 |
| `파일 내용을 읽지 못했습니다` | 그 **파일** 문제(스캔본·빈 문서) | OCR 가능한 형식으로 다시 |
| `처리 중 오류가 발생했습니다(XxxError)` | 분류 못 한 오류 | ②의 로그에서 그 이름으로 검색 |

### 로그에 `content 없음` / `max_tokens` 이 보이면

**추론 모델은 추론 토큰도 `max_tokens` 를 함께 씁니다.** 한도가 빠듯하면 생각만 하다
끝나 본문이 비어서 오고(`finish_reason=length`), 업로드가 실패합니다.

클라이언트가 한도를 두 배씩 늘려 다시 시도하지만(최대 8000), 매번 늘리면 그만큼 느리니
`.env` 에서 처음부터 넉넉히 주는 편이 낫습니다. **상한일 뿐이라 모델이 일찍 멈추면
남는 만큼은 비용이 없습니다.**

```ini
VLLM_TASK_MAX_TOKENS=2000    # 구조화 응답(적재 자동채움·도구 선택·SQL)
VLLM_MAX_TOKENS=1500         # 채팅 답변
```

> 예외를 통째로 삼키던 자리가 있어서, 예전에는 화면에도 로그에도 원인이 안 남았습니다.
> 지금은 화면에 분류된 원인이, 서버 로그에 전체 내용이 남습니다.
> 다만 **문서 본문은 화면에 내보내지 않습니다** — vLLM/TEI 오류 본문에 요청에 실린
> 문서 조각이 섞여 나올 수 있어, 남의 문서가 다른 사람 화면에 보일 수 있기 때문입니다.

## 8. 운영 참고

- Django auth DB를 Postgres로 쓰려면: `DJANGO_DB=postgres` (기존 DB에 django_* 테이블 추가).
- 운영 필수 env: `DJANGO_SECRET_KEY`(랜덤 문자열), `DJANGO_DEBUG=0`, `DJANGO_ALLOWED_HOSTS=사내주소`.
- 만료 문서 자동 정리(`scripts.lifecycle_sweep`)를 **cron 에 등록**하세요(위 5-2 참고).
- 대량(수만 건) 문서에서 문서 관리 화면이 느리면, 기존 DB에 인덱스가 없을 수 있습니다.
  신규 배포는 자동 생성되며, 기존 DB는 `documents(lifecycle_status, doc_type, expiry_date, updated_at)`에
  인덱스를 추가하면 됩니다.
- 사내 SSO(OIDC)는 `mozilla-django-oidc` 패키지로 연동 가능(추후 요청 시 구성).
